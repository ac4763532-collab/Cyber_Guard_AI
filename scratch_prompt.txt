# CYBERGUARD AI — BUILD FULL SECURITY EVENT DETAILS EXPERIENCE

## 1. PROJECT OBJECTIVE

Build a production-quality Security Activity Details interface for CyberGuard AI.

When a user clicks the **"View Full Details"** button on any event in:

1. Personal → My Devices → Device Details → Live Telemetry Stream.
2. Personal → Log Monitoring → Security Event Feed.

Open a professional, detailed explanation panel that helps ordinary, non-technical users understand exactly what happened on their computer.

The interface must support two viewing modes:

- Simple View — for ordinary computer users.
- Analyst View — for cybersecurity professionals.

Use the existing Windows Event Explanation Engine, existing 10 JSON knowledge-base files and real collected Windows event records.E:\CyberGuard\backend\app\agents\log_analysis\knowledge_base\windows in this location

Do not create another explanation engine or duplicate backend logic.

### C. Simple View — Default Mode

This must be the default mode for individual users.

Create six clearly separated sections.

#### 1. What happened?

Explain the activity in simple everyday language.

Use the explanation engine's output.

#### 2. Who was involved?

Display available information:

- Account name.
- Account type.
- Initiating user.
- Program or process.
- Source identity.

Explain unfamiliar terms in simple language.

#### 3. Where did it happen?

Display:

- Device name.
- Computer hostname.
- Source computer.
- Source IP address, if available.
- Windows log channel.

Distinguish between the monitored computer and the source computer.

#### 4. When did it happen?

Display:

- Actual event date.
- Actual event time.
- Time zone.
- Relative time, such as "5 minutes ago".

Use the original event timestamp.

#### 5. Why does it matter?

Explain the security significance.

Examples:

- A successful sign-in is not automatically suspicious.
- One failed sign-in does not prove an attack.
- A new service installation may be legitimate or suspicious depending on its details.
- Program execution is normal computer activity unless supporting evidence suggests otherwise.

Never exaggerate the risk.

#### 6. What should I do?

Show contextual recommendations based on the event and available evidence.

Examples:

- If you recognize the activity, no action may be required.
- If you do not recognize a sign-in, review the account activity.
- If repeated unfamiliar sign-in failures occur, investigate further.
- If an unfamiliar service was installed, verify which software created it.

Do not recommend disruptive actions without sufficient evidence.

Only display fields actually present.

Do not fabricate missing evidence.

### E. Expandable Original Event Evidence

Create an expandable section:

1. Original event metadata.

Use a readable monospace code viewer.

Add a copy button.

Never modify or reconstruct the original XML and present it as collected evidence.

## 5. SEVERITY AND ASSESSMENT DISPLAY

Keep these concepts separate.

### Severity

- Informational.
- Low.
- Medium.
- High.
- Critical.

### Assessment

- Normal.
- Unusual.
- Suspicious.
- Unknown.

### Threat status

- No threat established.
- Under investigation.
- Confirmed threat, only when supported by the existing incident/detection workflow.
